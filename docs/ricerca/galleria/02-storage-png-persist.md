## Raccomandazione progettuale — "Galleria": memorizzazione e visualizzazione foto

### 1. Formato foto sull'orologio (decisione)
**Emery (PT2): raw "6-bit packed"** (4 px → 3 B, MSB-first, 34.200 B per 200×228) come formato PRIMARIO di trasporto e di persist; sull'orologio si decomprime in un `GBitmap` **8Bit preallocato** (`gbitmap_create_blank(GSize(200,228), GBitmapFormat8Bit)` = 45.640 B, allocato UNA volta in `init()` come primo blocco grande) con il loop `dst[k] = 0xC0 | sestetto` (≈1-3 ms su HW, 0 ms in emulatore). Motivi: nessun decoder → nessun rischio di heap corruption, RAM deterministica (nessun buffer transiente da 25-45 KB), 134 chunk per foto invece di 179, qualità identica agli 8Bit (64 colori + dithering fatto sul telefono con Pillow/JS sulla palette `pebble_colors_64`).
**PNG8 solo come ottimizzazione facoltativa** (fase 2): riduce i chunk (~80-120 per 20-30 KB) ma richiede: (a) telefono che produca PNG **non interlacciato, colour type 3, ≤64 colori, UN SOLO IDAT** (libpng/zlib di default spezzano a 8 KiB!) — un encoder PNG in JS con IDAT unico e deflate "stored" o pako; (b) sull'orologio, PRIMA di `gbitmap_create_from_png_data`: CRC32 sull'intero blob (calcolato sul telefono e messo nell'indice), parsing dei chunk (firma, IHDR w/h/bitdepth/colortype 3, interlace 0, esattamente un IDAT, IEND), rifiuto altrimenti; (c) controllo `gbitmap_get_data(b) != NULL && bounds == 200x228` dopo la create (ritorna non-NULL anche in errore); (d) `free(png_buf)` subito dopo la create; (e) distruggere la foto precedente PRIMA di decodificare (picco RAM). Il tinflate del firmware non ha bound check: dati corrotti = crash dell'app.
**4BitPalette** (22.816 B, 90 chunk, 16 colori per foto): scartare per la galleria principale — 16 colori su foto reali è visibilmente peggio anche con dithering e il blit palettizzato costa 3-5× per pixel; tenerlo come opzione "modalità compatta" se serve raddoppiare il numero di foto.
**Flint (P2 Duo): raw 1-bit packed, 18 B/riga MSB-first, 3.024 B** (12 chunk) caricato in un `GBitmapFormat1BitPalette` 144×168 preallocato con palette `{GColorBlack, GColorWhite}` (`gbitmap_create_blank_with_palette` con array static, free_on_destroy=false). Dithering Floyd-Steinberg sul telefono; niente 2-bit (il firmware rende i grigi come scacchiera fissa), niente 4-bit/8-bit (NULL su PBL_BW, non disegnabili).

### 2. Schema persist (chiavi, chunk, indice, CRC)
```c
#define KEY_HEADER        0        // GalleryHeader (≤256 B): magic 'GAL1', schema u16, slots u8, interval_min u16, layout/font/12h flags, crc16
#define KEY_SLOT_BASE     1        // 1..MAX_SLOTS: SlotIndex (16 B packed)
#define KEY_CHUNK_BASE    1000     // chunk key = KEY_CHUNK_BASE + slot*256 + i   (256 chunk/slot = 64 KiB max)
typedef struct __attribute__((packed)) {
  uint8_t  state;      // 0 vuoto, 1 completo
  uint8_t  format;     // 1 = raw6 200x228, 2 = raw1 144x168, 3 = png8
  uint16_t w, h;
  uint32_t length;     // byte totali
  uint32_t crc32;      // sul payload
  uint16_t generation; // contatore per rilevare foto cambiata
  uint16_t reserved;
} SlotIndex;           // 16 B → record da 28 B
```
Regole: (1) i chunk arrivano via AppMessage (≤256 B di payload per messaggio) e si scrivono **subito, uno per messaggio, in ordine crescente di i**; (2) l'indice dello slot (con CRC32) si scrive **per ultimo**: l'atomicità del firmware è per record, quindi indice valido ⇒ foto completa; (3) all'avvio si leggono header + indici (chiavi piccole e contigue), si valida `persist_get_size(key)==sizeof`, magic e CRC, e si degrada a sfondo di default se qualcosa non torna; (4) la sostituzione di una foto sovrascrive le STESSE chiavi (niente `persist_delete`: le tombstone occupano 12 B e non liberano nulla fino alla compattazione); (5) leggere i chunk di una foto in ordine di scrittura (i=0..n-1) e tutto in una sequenza, senza intercalare altre chiavi (ogni lookup fuori ordine costa una scansione con wrap); (6) verificare CRC32 dopo la lettura completa e solo poi `layer_mark_dirty`.
**Budget**: `persist_get_max_size()` (con `PBL_API_EXISTS`) deve essere ≥ 1 MiB (fw ≥ 4.9.171; con SDK 4.33.1 il fw è comunque ≥ 4.32); altrimenti galleria disabilitata. Dimensionare **per tenere il file ≤ 512 KiB** (≈ 12 foto raw6 = 430 KB su disco, o 16 foto PNG da ~25 KB), non per riempire 1 MiB: il costo di scansione cresce come record × pagine (≈ 125.000 hop a 512 KiB vs 500.000 a 1 MiB) e la riscrittura per crescita/compattazione da 1 MiB è "many seconds". Limite hard per slot nel codice: 256 chunk. Al 75% della quota entrano comunque 21 foto raw6 / 16 foto 8Bit / 25 PNG8.
**Costi da mettere in conto (stime HW)**: scrittura di un chunk nuovo ≈ 1-2 ms di program + scansione (≈ 15-80 ms su emery per file da 128-512 KiB, ~0,1-2 s su flint per file grandi → su flint tenere il file sotto ~64 KiB, cosa naturale con 3 KB/foto); crescite del file (4→8→…→512 KiB) durante il primo riempimento: copie cumulative ≈ 1 MiB + erase di ~250 subsector (tSE 30 ms tip / 400 ms max) → alcuni secondi in totale, bloccanti (il firmware sospende il task watchdog per 60 s); compattazione quando lo spazio morto supera ~20% dell'allocazione (≈ ogni 3-5 foto sostituite a 512 KiB): riscrittura di tutto il file, secondi. Conseguenza sul protocollo di trasferimento: ACK applicativo per chunk (il telefono manda il chunk i+1 solo dopo l'ACK di i), timeout lato telefono ≥ 10-15 s, ripresa dall'ultimo chunk confermato, e mai trasferire nel tick handler.
**Lettura a rotazione**: foto da 134 chunk in fondo a un file da 512 KiB ≈ 0,1-0,2 s su emery (letture flash memory-mapped); accettabile una volta ogni intervallo (minuti), ma per non bloccare l'UI leggere in un `AppTimer` a lotti (es. 24 chunk ogni 30 ms, decomprimendo direttamente nel bitmap 8Bit preallocato) e fare un solo `layer_mark_dirty` alla fine.

### 3. Rendering
- Emery: `Layer` custom (o `BitmapLayer`) che disegna la foto con `GCompOpAssign` in un unico `graphics_draw_bitmap_in_rect` (≈1-3 ms), poi l'ora. Due strade per l'ora: (a) font di sistema/custom con `graphics_draw_text` e colore scelto con `gcolor_legible_over(colore_medio)` — il colore medio si calcola UNA volta al caricamento della foto leggendo i byte 8Bit sotto il rettangolo dell'ora (media di r,g,b a 2 bit ciascuno, luminanza ≈ (3r+4g+b) come fa il firmware); (b) **sprite cifre 1BitPalette** (palette `{GColorClear, colore}`, `GCompOpSet`) ricolorabili a runtime scrivendo `palette[1]` — verificato: la palette è letta al blit, nessuna copia dei pixel; alone/contorno: 4 blit sfalsati di 1 px con `palette[1]=colore_contrario` e poi il blit principale (5 blit/cifra, ~1-2 ms totali). Sprite sheet: un solo bitmap per font + `gbitmap_create_as_sub_bitmap` per le cifre (nessuna copia). Una cifra 60×110 a 1 bpp = 880 B → 10 cifre + ':' ≈ 10 KB; layout "full screen" con cifre 90×160 = 1.800 B/cifra → 20 KB (rientra nel budget se il PNG temporaneo non è usato; con raw6 non serve). Mai `GCompOpAssign` con palette trasparente (GColorClear diventa nero).
- Flint: foto 1BitPalette con `GCompOpAssign`; testo/sprite con palette `{GColorClear, GColorWhite|GColorBlack}` e `GCompOpSet` (il bitblt 1-bit onora la trasparenza per i palettizzati; NON usare bitmap 1Bit non palettizzati per gli sprite: GCompOpSet lì è un OR). Colore automatico = conteggio dei pixel bianchi sotto l'area dell'ora (bit MSB-first nel 1BitPalette); sempre con alone di 1 px sul dithering.
- `MINUTE_UNIT`, un solo `layer_mark_dirty` per tick; cambio foto governato da un contatore di minuti nel tick (niente timer aggiuntivi in stato stazionario); `text_layer_set_should_cache_layout` se si usa TextLayer.

### 4. Budget RAM (emery, statico ~30 KB → heap ≈ 101 KB)
Foto 8Bit 45.640 + sprite cifre 10-20 KB + buffer chunk 256 B + AppMessage inbox 2.048+256 (+ dict) ≈ 2,5 KB + UI/font ≈ 3 KB ≈ 62-72 KB → margine 30-40 KB. Con il path PNG aggiungere 25-30 KB transienti solo mentre la foto vecchia è già stata distrutta. Ordine di allocazione fisso in `init()`: foto (45.640) → sprite → resto; mai `realloc`. Flint (heap ≈ 35 KB): foto 3.072 + sprite ~4 KB + AppMessage 2,5 KB + UI 2 KB ≈ 12 KB.

### 5. Checklist di sicurezza/robustezza
1. `#if PBL_API_EXISTS(persist_get_max_size)` e controllo ≥ 1.048.576, altrimenti modalità "solo sfondo di default".
2. Ogni `persist_write_data` controlla il ritorno (256) e gestisce `E_OUT_OF_STORAGE` (stop trasferimento, notifica telefono).
3. CRC32 (tabella 256×4 B = 1 KB in flash, o variante nibble 64 B) su ogni foto; indice scritto per ultimo; validazione all'avvio.
4. Mai passare a `gbitmap_create_from_png_data` dati non validati (IHDR/IDAT unico/CRC): il decoder corrompe l'heap su input malformati; controllare `gbitmap_get_data()!=NULL` dopo la create.
5. Distruggere il bitmap precedente prima di crearne uno nuovo; preallocare i blocchi grandi in `init()` (frammentazione osservata: malloc da 45,6 KB fallita con 57 KB liberi).
6. Palette degli sprite in array `static`, `free_on_destroy=false`; non chiamare `gbitmap_set_palette` su bitmap con palette heap (decoder PNG / create_blank) se non si vuole liberarla.
7. Scritture persist solo durante il sync (mai nel tick); debounce per le impostazioni (chiave header) ≤ 1/min; flush in `deinit`.
8. Su flint tenere il file persist piccolo (≤ 64 KiB) per via delle letture QSPI transazionali.

### 6. Numeri chiave da riportare nel design doc
- 200×228: 8Bit 45.600 B (45.640 con struct); 4BitPalette 22.800+16; 2Bit 11.400; 1BitPalette 5.700; 1Bit 6.384 (stride 28); raw6 34.200. 144×168: 1BitPalette 3.024 (+2); 1Bit 3.360 (stride 20).
- PNG decode: buffer = (stride×h + h) B, +~1,7 KB transiente; PNG liberabile subito; 7 ms in emulatore per 18,7 KB.
- Persist: 268 B per chunk da 256 B, max 3.912 chunk, 1 MiB per app (fw ≥ 4.9.171), file growable 4 KiB→1 MiB, compattazione a ~20% di dead space; tPP 0,25/2 ms, tSE 30/400 ms (GD25Q256E).
- Foto per quota ≤75%: raw6 21, 8Bit 16, PNG8(~30 KB) 25, 4Bit 32; flint 1-bit 246.

## Open questions
- Tempi reali su hardware (PT2 e P2 Duo) di: decodifica PNG 200x228, persist_write_data con file da 128/256/512 KiB (scansione header + program), crescita del file (grow) e compattazione, lettura sequenziale di 134 chunk. In emulatore la flash è istantanea: servono misure con `time_ms()` su orologio reale (Dev Connect) prima di fissare l'intervallo minimo di rotazione e i timeout del protocollo di trasferimento.
- Il costo per 'hop' di pagina PFS su SF32LB52 (lettura memory-mapped + mutex + prv_erase_pause + new_timer_start in flash_read_bytes): stimato 1-3 µs ma non misurato; se fosse ~10 µs le scansioni a 512 KiB salirebbero a ~1 s per chiave nuova e converrebbe limitare il file a 256 KiB (8 foto raw6).
- Comportamento di AppMessage durante una riscrittura del file persist di più secondi (grow/compact con watchdog sospeso): i messaggi in arrivo vengono NACKati o persi? Serve un test end-to-end con l'app mobile Core (Kotlin) e non solo con pypkjs, per tarare timeout e retry lato telefono.
