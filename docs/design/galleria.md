## 1. Idea

Watchface (archetipo W + sync S) per **Pebble Time 2** (`emery`, 200×228, 64 colori) e **Pebble 2 Duo** (`flint`, 144×168 B/N). Foto scelte e ritagliate dall'utente **dal telefono** (config page nell'app Pebble), trasferite via AppMessage, **memorizzate sull'orologio** (persist, 12 slot) e mostrate **a schermo intero, a rotazione** con intervallo configurabile. Sopra la foto: **ora grande e nitida** in due layout — **A** "un terzo" (cifre 68 px + riga info passi/batteria/data) e **B** "tutto schermo" (HH sopra MM, cifre 96 px) — con **scelta font** (3 + LECO di sistema), **colore testo automatico** (bianco/nero in base alla foto, contorno quando serve), **12/24 h** e **zero iniziale**. `MINUTE_UNIT`, **mai i secondi**, nessuna animazione; tutto funziona senza telefono (foto e impostazioni in persist; 2 foto demo incluse). L'utente usa **Android e iPhone**.

## 4. Modello dati

### 4.1 Struct C (tutte `packed`, validate con `persist_get_size() == sizeof`)
```c
#define GAL_MAX_SLOTS      12
#define GAL_KEYS_PER_SLOT  256
#define GAL_KEY_SCHEMA     0
#define GAL_KEY_MANIFEST   1
#define GAL_KEY_ROTSTATE   2
#define GAL_KEY_SETTINGS   10
#define GAL_KEY_CHUNK(k,i) (1000u + (uint32_t)(k) * GAL_KEYS_PER_SLOT + (i))
#define GAL_MAGIC          0x314C4147u          /* 'GAL1' */
enum { PHOTO_FMT_NONE = 0, PHOTO_FMT_RAW6_200x228 = 1, PHOTO_FMT_RAW1_144x168 = 2 };

typedef struct __attribute__((packed)) {
  uint8_t  state;        /* 0 vuoto, 1 valido */
  uint8_t  format;       /* PHOTO_FMT_* */
  uint16_t generation;   /* +1 a ogni sostituzione */
  uint32_t length;       /* 34200 | 3024 */
  uint32_t crc32;        /* sul payload */
  uint32_t photo_id;     /* assegnato dal telefono (≠ 0) */
} GalSlotMeta;           /* 16 B */

typedef struct __attribute__((packed)) {
  uint32_t    magic;  uint8_t schema;  uint8_t slot_count;   /* GAL_MAGIC, 1, 12 */
  uint8_t     order[GAL_MAX_SLOTS];                          /* indici slot in ordine di rotazione, 0xFF = fine */
  uint16_t    reserved;
  GalSlotMeta slots[GAL_MAX_SLOTS];                          /* 192 B */
  uint16_t    crc16;
} GalManifest;                                               /* 214 B, chiave 1, scritto PER ULTIMO */

typedef struct __attribute__((packed)) {
  uint8_t  schema;        /* 1 */
  uint8_t  layout;        /* 0 A, 1 B */
  uint8_t  font;          /* 0 Anton, 1 Bebas Neue, 2 Barlow Condensed, 3 LECO sistema (solo A) */
  uint8_t  clock_mode;    /* 0 auto (clock_is_24h_style), 1 12 h, 2 24 h */
  uint8_t  leading_zero;  /* 0 auto (on in 24 h, off in 12 h), 1 on, 2 off */
  uint8_t  text_color;    /* 0 auto, 1 bianco, 2 nero, 3 giallo pastello, 4 blu Oxford */
  uint8_t  outline;       /* 0 auto (> 15 % conflitti), 1 sempre, 2 mai */
  uint16_t interval_min;  /* 0 mai; 5, 15, 30, 60, 180, 1440 */
  uint8_t  order;         /* 0 sequenziale, 1 casuale */
  uint8_t  shake_next;    /* 0/1 */
  uint8_t  info_row;      /* bit0 passi, bit1 batteria, bit2 data, bit3 BT */
  uint8_t  reserved[6];   /* v1.2 (S1): con [4] la struct era 18 B, non 20 */
  uint16_t crc16;
} GalSettings;            /* 20 B, chiave 10 (_Static_assert in settings.c) */

typedef struct __attribute__((packed)) { uint16_t shake_offset; uint16_t crc16; } GalRotState; /* 4 B, chiave 2, solo deinit; S4: shake a 16 bit modulo 27.720 = mcm(1..12) (con 8 bit il wrap 255→0 annullava una scossa per n | 255); manual_pos rimosso */

```

### 4.2 Persist (chiavi)
```
0        uint32 schema (= 1)
1        GalManifest (214 B)   ← scritto per ultimo: manifest valido ⇒ foto complete
2        GalRotState (4 B)     ← solo in deinit
3–9      riservate
10       GalSettings (20 B)    ← al ricevimento (raro) e in deinit; mai nel tick
11–99    riservate
1000 + k·256 + i   chunk i (256 B) dello slot k (k 0..11, i 0..255 → 64 KiB/slot; raw6 usa 134, raw1 12)
```
Regole: chunk in ordine crescente di `i` → manifest; avvio: `persist_exists` + `persist_get_size == sizeof` + magic + CRC16 altrimenti default (mai crash; schema futuro → reset); caricamento foto: 134 letture in ordine senza intercalare altre chiavi, CRC32 accumulato, `layer_mark_dirty` solo se coincide (altrimenti slot invalido in RAM → successivo); sostituzione = stesse chiavi (≈ 36 KB di spazio morto per foto sostituita → compattazione dopo ~3 sostituzioni: secondi ❓, coperti dal backoff PKJS); `#if PBL_API_EXISTS(persist_get_max_size)` e valore ≥ 1.048.576 altrimenti modalità demo; `E_OUT_OF_STORAGE` sempre gestito. Occupazione: 12 × 35.808 + 238 ≈ **430 KB** (41 %; allocazione 512 KiB); flint ≈ 38 KB. Se in S8 il costo per chiave nuova risultasse ~1 s, scendere a 8 slot.
**S4 (`storage.c`)**: API `storage_init()` (quota, schema → reset se futuro, manifest validato) · `storage_manifest()`/`storage_valid_slots()` · `storage_read_settings()`/`storage_settings_changed()` (AppTimer 10 s, `app_timer_reschedule` se già pendente) /`storage_flush()` (deinit) · `storage_read_rotstate()`/`storage_write_rotstate()` (solo deinit, se cambiato) · `storage_read_chunk(slot, i, buf, cap)` · `storage_write_chunk(slot, i, data, n ≤ 256)` → `storage_commit_slot(slot, format, length, crc32, photo_id)` (state VALID, `generation+1`, slot aggiunto in coda a `order[]` se assente, manifest scritto; su errore la copia RAM viene ripristinata) · `storage_set_order()`/`storage_clear_slot()` (S5a). Codici `StorageResult` OK/ERR/NO_SPACE/DISABLED. ⚠️ `persist_write_int`/`persist_write_data` ritornano i **byte scritti** in caso di successo (non `S_SUCCESS`): controllare `< 0`. Lettura foto: `ui_photo_load_persist(slot, meta)` con buffer static da 256 B → `PhotoDecoder` a streaming → CRC32 (emulatore: 8–13 ms per 134 chunk su emery, 1 ms su flint); scrittura di 134 chunk + manifest in emulatore ≈ 1,0–1,2 s con crescita del file, 145 ms sovrascrivendo. Testabile su host con lo shim `test/shim/pebble.h` (persist in memoria, quota, `E_OUT_OF_STORAGE` iniettabile, timer).

### 4.3 Formato raw6 (emery)
`idx = (r2<<4)|(g2<<2)|b2` (RGB 0/85/170/255 esatti: `GColorFromRGB` **tronca** `>>6`). Riga-maggiore, 4 px → 3 B: `b0 = p0<<2 | p1>>4; b1 = (p1&15)<<4 | p2>>2; b2 = (p2&3)<<6 | p3`. Riga 150 B, totale 34.200 B. Byte del `GBitmap` 8Bit = `0xC0 | idx`.
### 4.4 Formato raw1 (flint)
`GBitmapFormat1BitPalette` 144×168: MSB-first (pixel 0 nel bit 0x80), riga 18 B, 3.024 B, palette `static {GColorBlack, GColorWhite}` (`gbitmap_create_blank_with_palette`, `free_on_destroy=false`). ⚠️ Non `GBitmapFormat1Bit` (LSB-first, stride 20 B).

> **v1.8 (29/08/2026, revisione post code-review: `SYNC_REQUEST.OFFSET`, outbox esatto, rotazione congelata in sync, attesa dell'HELLO, classi di retry — nessuna messageKey nuova); v1.7 (S5b: `HELLO.CRC`, lato telefono in §5.1); v1.6 (S5a)** — sezione riscritta sul codice reale (`sync_proto.c` puro + `sync.c` glue + `src/pkjs/sync.js`). **Deviazione da D9**: `app_message_close()` **non è esportata dall'SDK 4.33.1** (assente da `pebble.h` e da `libpebble.a`: esiste solo dentro il firmware) e `app_message_open()` ritorna `APP_MSG_INVALID_STATE` se già aperta ⇒ nessuna "inbox a due fasi": **una sola inbox**, aperta in `init()` e mai chiusa. `MSG` (`SyncMsg`): 1 JS_READY · 2 HELLO · 3 SYNC_REQUEST · 4 SYNC_READY · 5 PHOTO_BEGIN · 6 PHOTO_DATA · 7 PHOTO_END · 8 STATUS · 9 SYNC_DONE · 10 SETTINGS · 11 ALBUM_ORDER · 12 ALBUM_DELETE.

**Tipi sul filo.** Il JS serializza ogni `Number` come **int32** (doc SDK "Number → int32"): l'orologio legge gli interi in base a `Tuple.length` (1/2/4 B, `prv_tuple_u32`) e gli `uint8` saturano a 255 (256 non deve diventare lo slot 0); `CRC`/`PHOTO_ID`/`LENGTH`/`OFFSET` vanno inviati come `x | 0` (bit pattern a 32 bit, riletto come `uint32`). Gli array JS diventano `TUPLE_BYTE_ARRAY`. L'orologio scrive `dict_write_uint8/16/32`. I dizionari con più chiavi possono arrivare in qualsiasi ordine; le chiavi assenti sono "campo mancante" (`SyncIn.fields`).

**Orologio → telefono** (outbox **esatta**: 110 B = `dict_calc_buffer_size(6, 1,1,1,2,2, SYNC_SLOTS_BYTES)` calcolata in `sync_init`; HELLO è per costruzione il messaggio più grande — STATUS 44 B, SYNC_READY 18 B. Gli esiti delle `dict_write_*` sono accumulati: un messaggio incompleto lascia il WARNING `sync: dict_write -> %d, msg %u incompleto` (tripwire per l'emulatore, hook `GALLERIA_DEBUG_OUTBOX=100`) ma parte comunque, perché dopo `outbox_begin` il firmware è in OUT_WRITING e se ne esce solo con `outbox_send` — revisione 29/08, F4):
- `HELLO{MSG 2, PROTO u8 = 1, FORMAT u8, MAX_CHUNK u16, CRC u16, SLOTS 60 B}` — `FORMAT` = `PHOTO_FMT_*` nativo (1 raw6 emery, 2 raw1 flint: il telefono non indovina dalla piattaforma); `CRC` = CRC-16/CCITT-FALSE dei primi 18 B delle impostazioni correnti (v1.7, S5b: vedi sotto); `SLOTS` = 12 × `{state u8 (0/1), crc32 u32 LE}` dal manifest; `MAX_CHUNK 0` = trasferimento foto non supportato (album disabilitato per quota < 1 MiB, o telefono senza 8k). 110 B = outbox.
- `SYNC_READY{MSG 4, MAX_CHUNK u16}` — valore effettivo (può essere rinegoziato).
- `STATUS{MSG 8, CODE u8, SLOT u8 (0xFF se non pertinente), OFFSET u32, REPLY_TO u8}` — `OFFSET` = prossimo offset atteso per la foto in corso (0 se nessuna); **`REPLY_TO`** (S5b, v1.7) = `MSG` del messaggio a cui lo STATUS risponde: il telefono, mentre attende la risposta a un messaggio preciso, **scarta gli STATUS di altri messaggi** (le copie ritrasmesse di `SETTINGS`/`ALBUM_ORDER` hanno lo stesso `SLOT 0xFF` e senza `REPLY_TO` la seconda risposta veniva letta come esito del passo successivo — revisione S5b). 44 B.

**Telefono → orologio** (inbox 4.153 B):
| Messaggio | Stato | Effetto / risposta |
|---|---|---|
| `JS_READY{MSG 1}` | qualsiasi | rinegozia il chunk, risponde `HELLO` |
| `SYNC_REQUEST{COUNT u8, OFFSET u32 opz.}` | qualsiasi | album disabilitato o chunk 0 → `STATUS{NOT_SUPPORTED}`; altrimenti → stato **SYNCING** (idempotente: foto in corso abbandonata; "Foto k/n" riparte da k = `OFFSET` = foto già concluse, clampato a `COUNT − 1`, 0 se assente — v1.8, F3), `SYNC_READY{MAX_CHUNK}`, timer di silenzio 30 s armato |
| `PHOTO_BEGIN{SLOT, PHOTO_ID, FORMAT, LENGTH, CRC, OFFSET}` | SYNCING (altrimenti `BUSY`) | campo mancante, `SLOT ≥ 12`, `FORMAT ≠ nativo`, `LENGTH ≠ photo_format_length`, `PHOTO_ID 0` → `BAD_FORMAT`; stima `slot_dopo × (LENGTH + ⌈LENGTH/256⌉ × 16) > 75 % di persist_get_max_size()` → `NO_SPACE`; **ripresa** se `SLOT`/`PHOTO_ID`/`CRC` coincidono con il `pending` attivo e `OFFSET == pending.next` (anche `OFFSET == 0`: ritrasmissione di un `PHOTO_BEGIN` il cui `STATUS` si è perso) — CRC parziale conservato e "Foto k/n" fermo; altrimenti nuovo `pending` da 0: **se lo slot era VALID viene prima svuotato nel manifest** (`storage_clear_slot`: un'interruzione lascia uno slot vuoto che la rotazione salta e che `HELLO` annuncia state 0, mai un manifest che certifica un payload misto) e "Foto k/n" avanza solo se la foto (slot + photo_id) è diversa dall'ultima conteggiata; risposta **sempre** `STATUS{OK, SLOT, OFFSET = pending.next}`: il telefono manda i dati da lì |
| `PHOTO_DATA{SLOT, OFFSET, DATA}` | SYNCING (altrimenti `BUSY`) | senza `pending` → `SEQ_ERR{OFFSET 0}`; slot diverso → `SEQ_ERR{next}`; `OFFSET < next` → **duplicato: nessuna risposta, nessuna scrittura**; `OFFSET > next`, `OFFSET % 256 ≠ 0`, `n = 0`, `n > MAX_CHUNK`, `OFFSET + n > LENGTH`, `n % 256 ≠ 0` senza essere l'ultimo pezzo → `SEQ_ERR{next}`; altrimenti `⌈n/256⌉` × `storage_write_chunk(slot, OFFSET/256 + j, …)` **direttamente dal buffer dell'inbox** (nessuna copia; l'ACK parte al ritorno del callback ⇒ flash scritto prima del chunk successivo), CRC32 accumulato, `next += n`, **nessuna risposta** (basta l'ACK); `E_OUT_OF_STORAGE` → `NO_SPACE`, altro errore → `STORAGE_ERR`, in entrambi i casi `pending` abbandonato |
| `PHOTO_END{SLOT, PHOTO_ID}` | SYNCING (altrimenti `BUSY`) | senza `pending`: se lo slot è VALID con lo stesso `PHOTO_ID` → `STATUS{OK, OFFSET = LENGTH}` (ritrasmissione dopo un commit il cui STATUS si è perso: idempotente), altrimenti `SEQ_ERR{0}`; `next ≠ LENGTH` → `SEQ_ERR{next}`; CRC diverso → `CRC_ERR` (manifest **non toccato**: lo slot resta vuoto se era una sostituzione, `pending` abbandonato); CRC uguale → `storage_commit_slot` (state VALID, generation + 1, `order[]`, **manifest per ultimo**) → `STATUS{OK, SLOT, OFFSET = LENGTH}`; commit fallito → `NO_SPACE`/`STORAGE_ERR` (copia RAM del manifest ripristinata). Il modello (`model_album_changed`: ricarica + redraw) viene avvisato **una volta a fine sync** (SYNC_DONE o timeout), non nel callback di ogni END. Durante la sync la rotazione è **congelata** (`model_sync_hold(true)` dopo ogni messaggio in SYNCING): tick, shake, focus e impostazioni aggiornano solo lo stato del modello e vengono applicati al rilascio (`model_album_changed` se il manifest è cambiato, altrimenti `model_sync_hold(false)` → log `rot(sync)`), come fuori focus (D10). Prima un tick a metà sostituzione leggeva il manifest in RAM con lo slot già svuotato e mostrava un'altra foto o la demo (revisione 29/08, F1) |
| `SYNC_DONE{MSG 9}` | SYNCING | → IDLE, "Foto k/n" spento, timer spento; **nessuna risposta**; in IDLE ignorato |
| `SETTINGS{SETTINGS 20 B}` | qualsiasi | blob = `GalSettings` (schema 1, campi in range, `crc16` ignorato: lo ricalcola `storage`); `settings_apply` → `sync_env_settings_changed(prima)` → UI: `ui_time_tick` se cambiano 12/24 h, zero iniziale, riga info; `ui_time_layout_changed` se layout/font; `ui_time_style_changed` se colore/contorno; altrimenti redraw completo; `model_settings_changed` se intervallo/ordine/shake. Risposta `STATUS{OK}` o `BAD_FORMAT` |
| `ALBUM_ORDER{ORDER 12 B}` | qualsiasi | indici < 12 senza duplicati, poi solo 0xFF → `storage_set_order` → `model_album_changed` (differito se in SYNCING) → `OK`; altrimenti `BAD_FORMAT`. **`order[]` è la lista autorevole della rotazione**: uno slot VALID non elencato non viene mostrato (S5b deve inviare sempre l'ordine completo; `storage_commit_slot` aggiunge in coda gli slot nuovi non presenti) |
| `ALBUM_DELETE{SLOT}` | qualsiasi | `SLOT < 12` → `storage_clear_slot` (state EMPTY, chunk lasciati, `order[]` invariato: la rotazione filtra per VALID) → `model_album_changed` → `OK`; se era lo slot del `pending`, il trasferimento decade |
| altro `MSG` | qualsiasi | `STATUS{NOT_SUPPORTED}` |

**Timeout di silenzio**: 30 s senza messaggi in SYNCING → IDLE, foto in corso abbandonata, "Foto k/n" spento (`sync_proto_timeout`, AppTimer riarmato a ogni messaggio con `app_timer_reschedule`; se il timer è già scaduto con il callback ancora in coda dietro il messaggio in corso, `reschedule` ritorna false → `app_timer_cancel` + nuovo `register`, e un contatore di generazione passato come contesto fa ignorare un eventuale callback stantio, che altrimenti forzava un IDLE spurio subito dopo un messaggio — revisione 29/08, F2; stesso schema nel debounce delle impostazioni di `storage.c`). Un `PHOTO_BEGIN` successivo riceve `BUSY`: il PKJS rinnova la `SYNC_REQUEST{COUNT, OFFSET = photoIndex}` e riprende dall'offset corrente (il `pending` è perso, quindi la foto riparte da 0, ma "Foto k/n" riprende da k).

**Riga info**: "Foto k/n" (`ui_time_set_sync_progress`) al posto di passi/icona BT nel layout A per tutta la sync (k = foto in corso, n = `COUNT`; dopo un BUSY riparte da `OFFSET` della `SYNC_REQUEST`; resta indietro di uno per ogni foto saltata dal telefono senza un `PHOTO_BEGIN` accettato — cosmetico, §10); in B nulla.

**Lato telefono (`src/pkjs/sync.js`, S5a; album vero in S5b)**: `ready` → `JS_READY`; **HELLO atteso entro 10 s dall'ACK** del `JS_READY` (l'HELLO nasce solo dal `JS_READY` e l'outbox dell'orologio non ritenta: 2 rinvii di `JS_READY`, poi `provider.onReadyFailed(why)` → retry lungo di `index.js`; nessun rinvio se l'HELLO arriva prima dell'ACK o se ha `PROTO` diverso — revisione 29/08, F5); `HELLO` → `provider.plan(hello)` = `{photos, settings, order, deletes}` (formato da `HELLO.FORMAT`; decodificare base64url **solo** le foto da inviare, una per volta); prima `SETTINGS`/`ALBUM_ORDER`/`ALBUM_DELETE` (ognuno attende il suo `STATUS`), poi `SYNC_REQUEST{COUNT}` → `SYNC_READY` → per ogni foto `PHOTO_BEGIN` → `STATUS{OK, OFFSET}` → `PHOTO_DATA` da `OFFSET` a passi di `MAX_CHUNK` (il successivo dal callback di successo, mai da timer) → `PHOTO_END{SLOT, PHOTO_ID}` → `STATUS` → foto successiva → `SYNC_DONE`. Regole che reggono il PKJS (S5a, verificate in emulatore): **un solo `PHOTO_DATA` in volo** (dopo una ripartenza il messaggio di ripresa può partire mentre l'ultimo chunk della generazione precedente è ancora in volo: il suo ACK viene ignorato), ma lo `STATUS` di un chunk fuori sequenza arriva *dopo* l'ACK di quel chunk (quindi dopo l'invio del successivo): il flusso dati ha una **generazione** `gen` che cambia a ogni ripartenza (`SEQ_ERR`/`BUSY`/`CRC_ERR`) e fa ignorare l'ACK dei chunk spediti prima; **ogni gestore di STATUS rifiuta le risposte non pertinenti** (S5b: prima di tutto per `REPLY_TO ≠ MSG atteso`; poi `SEQ_ERR`/`CRC_ERR` mentre si attende l'OK di un `PHOTO_BEGIN`; `OK` con `OFFSET ≠ LENGTH` mentre si attende quello dell'`END`; `SLOT ≠ 0xFF` per `SETTINGS`/`ALBUM_ORDER`, `SLOT ≠ slot` per `ALBUM_DELETE`; tutto tranne `NOT_SUPPORTED`/`BAD_FORMAT`/`STORAGE_ERR` mentre si attende `SYNC_READY`) lasciando intatta l'attesa e il suo timer; un `SYNC_READY` ripetuto non tocca l'attesa di un altro messaggio. Backoff 1-2-4-8-8-8-8 s sui fallimenti di `sendAppMessage`, poi (S5b) **la sync si chiude con errore** (telefono scollegato: inutile provare le foto rimaste una per una) e `index.js` la ritenta con backoff lungo 30 s-1-2-5-10 min (`JS_READY` → `HELLO` → diff: costa nulla se non c'è niente da fare), azzerato da una sync riuscita — **tre classi di esito** (29/08, F9): *link* (`summary.error` = `send failed`/`watchdog`, o `JS_READY` non consegnato) senza tetto = ripresa alla riconnessione; *photo* (esiti per foto/impostazioni/ordine/eliminazione con codice non permanente: `STORAGE_ERR`, `CRC_ERR`, `BUSY`, `load: …`; `summary.photoCodes = ['slot:CODE', …]`) al più 3 retry consecutivi (`photoRetries`, azzerato da un esito *link* o da una sync riuscita) poi si rinuncia fino al prossimo HELLO spontaneo; *permanent* (`NOT_SUPPORTED`, `BAD_FORMAT`, `NO_SPACE`) nessun retry; `STATUS` atteso entro 10 s (2 rinvii, poi `send failed`); `SEQ_ERR` → `PHOTO_BEGIN{OFFSET = status.OFFSET}` e ripresa; `CRC_ERR` → una ripetizione da 0; `BUSY` → nuova `SYNC_REQUEST{COUNT, OFFSET}` (l'orologio è tornato IDLE; se la richiesta di ripresa non viene consegnata la sync si chiude come per ogni invio fallito, non scarta la foto — 29/08); altri codici → foto scartata; a fine sync **nessuna attesa di STATUS sopravvive** (`cancelWait` in `finish`: uno STATUS tardivo non richiama un gestore stantio né riapre un'attesa — 29/08, F7); watchdog 60 s **senza ACK né messaggi dall'orologio** (il motore ha smesso di spedire: p.es. `load` che non torna) → sync chiusa con errore (un `HELLO` successivo o il retry può ripartire). Base64url decodificato in JS puro (`b64.js`: nel PKJS non esiste `atob`).

**Tempi attesi** ⚠️: 34,2 KB in 9 messaggi ≈ 9 round trip (ACK dopo 16 `persist_write_data` ≈ 80–110 ms su PT2) + trasferimento a 5–15 KB/s ≈ **4–9 s per foto** (contro 3–8 con chunk da 7.936: +1 round trip al secondo circa); 12 foto ≈ 50–110 s una tantum. Emulatore: vedi `PIANO.md` §4 (esito S5a).

**HELLO, v1.7 (S5b)**: `HELLO` porta anche **`CRC u16` = CRC-16/CCITT-FALSE dei primi 18 B di `GalSettings` correnti** (`settings_get()`, cioè tutto tranne il campo `crc16`): il telefono confronta con il CRC del proprio blob e manda `SETTINGS` **solo se diverso** — la sincronizzazione delle impostazioni è stateless come quella delle foto (dopo un `pebble wipe` il CRC dell'orologio torna quello dei default e il telefono rimanda le sue; uno `STATUS` perso non lascia flag sporchi). Outbox: 101 + 9 = 110 B, esatto (`SYNC_HELLO_VALUE_BYTES` = 67 in `sync_proto.h`, pin nel test host; 29/08). Un telefono con PKJS vecchio ignora il campo; un orologio vecchio (senza `CRC`) fa mandare `SETTINGS` a ogni sync (innocuo).

### 5.1 Lato telefono — album e diff (S5b, `src/pkjs/`)

Moduli ES5 (WebView Android, JavaScriptCore iOS, pypkjs): `index.js` (glue: eventi `Pebble`, modalità dev), `album.js` (**puro**: album sopra un'interfaccia `storage` `{getItem, setItem, removeItem}`, testabile in node), `sync.js` (motore §5, S5a) + `b64.js`, `crc.js` (CRC-32 zlib e CRC-16/CCITT-FALSE, stessi vettori di `crc.h`), `devserver.js` (client XHR del dev server, solo con `Pebble.platform === 'pypkjs'`). Bundle webpack con entry `index.js`: i moduli non richiesti (p.es. `test/fixture_photo.js`) non entrano nel `.pbw`.

**Album in `localStorage`** (nel PKJS dell'app Pebble: Android `SharedPreferences`, iOS `NSUserDefaults`; in pypkjs **persistente** in `~/.local/share/pebble-sdk/4.33.1/<piattaforma>/localstorage/<uuid>.{dat,dir}` — la nota di S5a "in emulatore non c'è" era sbagliata. ⚠️ È un `dbm.dumb` di CPython: l'indice `.dir` viene aggiornato solo per le chiavi nuove e alla chiusura pulita del runtime JS (che avviene a ogni `pebble install`), **non** per la riscrittura più lunga di un valore esistente ⇒ dopo `pebble kill` (SIGKILL) il JSON riletto è troncato. In modalità dev `index.js` fa quindi `removeItem` + `setItem` a ogni scrittura (`__delitem__` → `_commit()` riscrive `.dir`; la chiave riscritta passa da `_addkey`): durabile per qualsiasi lunghezza e charset — il padding a 64 KiB usato fino al 29/08 contava code unit UTF-16 mentre `dbm.dumb` conta byte UTF-8, quindi `città` o un JSON a cavallo del multiplo lo vanificavano (revisione 29/08, F11); se `setItem` lancia, il valore vecchio viene rimesso. I valori già paddati si rileggono (JSON.parse e b64.decode ignorano gli spazi). Costo: `.dat` che cresce a ogni scrittura (`pebble wipe` azzera). `pebble wipe` cancella anche il `localStorage`: per "orologio azzerato, telefono intatto" cancellare solo `qemu_spi_flash.bin`):
```
galleria.v1.album        JSON {v: 1,
                               photos: [12 × (null | {id, name? (≤ 64 car.), fmts: {"1": {len, crc, stored}, "2": {len, crc, stored}}, thumb? (≤ 6.000 car.)})],   // indice = slot; stored (S7, F12) = payload su disco
                               order: [slot…],            // ordine di rotazione (lista autorevole: §5 ALBUM_ORDER)
                               orderGen: n,               // cresce a ogni cambio dell'ordine: un ALBUM_ORDER confermato azzera orderDirty solo se l'ordine è ancora quello
                               settings: {layout, font, clock_mode, leading_zero, text_color, outline, interval_min, order, shake_next, info_row},
                               settingsSet: bool,         // l'utente ha espresso le impostazioni almeno una volta (payload con settings)
                               deleted: [slot…],          // ALBUM_DELETE non ancora confermati dall'orologio
                               orderDirty: bool}          // ALBUM_ORDER da mandare alla prossima sync
galleria.v1.watch        JSON {at, format, maxChunk, settingsCrc, slots: [12 × {state, crc}], foreign: [slot…]}   // ultimo HELLO (stato per la config page); chiave separata: riscritta a ogni HELLO senza toccare l'album
galleria.v1.p<slot>.<fmt>   payload base64url senza padding (fmt 1 = raw6, 2 = raw1); assente ⇒ "solo metadati" (dev: caricato a richiesta dal dev server)
```
Regole: `id` (= `photo_id`, uint32 ≠ 0) assegnato dalla pagina/dev server, altrimenti generato dal PKJS; `crc` = CRC-32 zlib del payload, salvato **senza segno** e inviato come `crc | 0`; JSON corrotto o `v` diverso ⇒ album azzerato (log), mai crash; **ordine delle scritture** (29/08, F6/F8): il payload nuovo si scrive PRIMA di toccare la foto vecchia dello slot (stessa chiave, si sovrascrive): `setItem` che lancia (quota) ⇒ quella voce non viene registrata e la vecchia resta intatta, metadati e payload; le rimozioni di payload (altro formato di una foto sostituita, voce dev senza `data`, slot eliminati) si eseguono solo DOPO il JSON dell'album; JSON che non si scrive ⇒ l'intera modifica è annullata (payload scritti rimossi o riportati al valore precedente, album riletto dal disco, `ok = false`, `changed = false`; `index.js` non fa `resync`); una foto a due voci (fmt 1 e 2) con quota su una sola resta registrata nel solo formato entrato ("da rifare il ritaglio", §10); cap 12 slot e 24 voci per payload, `data` accettata solo con la lunghezza base64 attesa (prima di decodificare), errori limitati a 32; una scrittura del JSON per `applyPayload`. Una foto del piano che risulta cambiata quando viene caricata (Save durante la sync) viene saltata (`load` → errore) e il prossimo `HELLO` rifà il piano; un payload locale corrotto viene rimosso insieme ai metadati del formato (senza loader) — mai una foto "zombie".

**Payload** (config page → `webviewclosed`, oppure dev server → `/state.json`), sempre `{v: 1, settings?, order?, deleted?: [slot…], photos?: [{slot, photo_id, fmt, len, crc, data?: <base64url>, url?: <solo dev>, name?, thumb?}]}`; una voce per **formato** (la stessa foto può avere due voci, fmt 1 e 2, stesso `photo_id`). `album.applyPayload(payload, {full})`:
- `full: false` (telefono, §6): delta — solo le voci presenti cambiano; `deleted` svuota gli slot elencati (metadati + payload) e li accoda a `deleted`; `order` sostituisce l'ordine; `settings` sostituisce le impostazioni.
- `full: true` (dev server; `index.js` lo usa solo se `state.full === true`): stato completo — gli slot **non** elencati vengono svuotati come se fossero in `deleted`, **ma solo se ogni voce è identificabile**: `photos` non array, voce non oggetto, slot non valido, troppe voci o payload interrotto ⇒ nessuna eliminazione implicita (errore `eliminazioni implicite saltate`); una voce rotta con slot valido conta come elencata e non tocca la foto locale (29/08, F10).
- Voce foto: `slot` 0..11, `fmt` 1|2, `len` = lunghezza del formato (34.200 / 3.024), `data` (se presente) decodifica a `len` byte con CRC-32 = `crc`, altrimenti scartata con log; **idempotente**: stesso `id` e stesso `crc` per quel `fmt` ⇒ nessuna modifica; `id` diverso ⇒ foto nuova nello slot (i payload dell'altro formato vengono rimossi); `order` assente ⇒ gli slot nuovi vengono accodati all'ordine; ogni cambiamento dell'album (foto nuova, eliminazione, riordino) mette `orderDirty`.
- `settings`: campi validati con gli stessi intervalli di `settings_validate()` (valori non validi ⇒ default del campo); nessun flag: il confronto è via `HELLO.CRC`.

**Piano** (`album.plan(hello)` = provider di `sync.js`, ricalcolato a ogni `HELLO`; `fmt = hello.format`):
1. Per ogni slot `k` con foto locale che ha `fmts[fmt]`: da inviare se `!(hello.slots[k].state === 1 && hello.slots[k].crc === fmts[fmt].crc)` (slot vuoto dopo un wipe, CRC diverso, foto sostituita) **e** il payload è disponibile — **S7 (F12): lo dicono i metadati** (`fmts[fmt].stored === true`, impostato da `setPayload` riuscito e rimosso col formato; `false` per le voci dev "solo metadati") oppure c'è un `loader` dev: `plan()`, `summary()`, `state()` e `applyPayload()` non leggono mai le chiavi dei payload (45,6 KB l'una, fino a 12 per HELLO; unica eccezione: i byte precedenti per il rollback F6/F8, riletti solo se i metadati dicono che esistono); un payload sparito alle spalle dell'album si scopre in `load()` → errore `payload assente`, `_dropCorrupt` rimuove i metadati di quel formato e il prossimo HELLO non la ripianifica (nessun ciclo di retry; con un loader i metadati restano e `stored` torna false); gli album scritti prima di S7 vengono migrati alla prima rilettura con una sonda `hasPayload` per formato, una sola volta, e riscritti (`v` resta 1); foto senza il formato dell'orologio (orologio cambiato) ⇒ log, nessun invio, nessun errore (la config page di S6 chiederà di rifare il ritaglio). Ogni foto del piano ha `load(cb)` invece di `bytes`: il motore decodifica **una foto per volta** e libera i byte dopo l'esito.
2. `deletes` = `deleted ∩ {k : hello.slots[k].state === 1}`; gli slot di `deleted` già vuoti sull'orologio escono subito dalla lista.
3. `order` (12 B, `0xFF` in coda) se `orderDirty` **oppure** il piano contiene foto o eliminazioni: ordine locale (solo slot con foto) + **slot VALID "estranei"** (sull'orologio ma non nell'album e non in `deleted`: p.es. telefono reinstallato) accodati, così restano visibili — **il telefono non elimina mai ciò che l'utente non ha eliminato**; gli slot estranei vengono annotati in `watch` per la config page.
4. `settings` (20 B, `crc16` compilato) se **`settingsSet`** e `hello.settingsCrc` è assente o diverso da `crc16(blob[0..18))` — un telefono che non le ha mai impostate (app reinstallata, `localStorage` perso) **non** sovrascrive con i default quelle dell'orologio; dopo il primo Save della config page il telefono è l'autorità.
5. `watch` ← snapshot dell'HELLO. Esiti (`onDone(summary)`): `ALBUM_ORDER` OK ⇒ `orderDirty = false`; `ALBUM_DELETE k` OK ⇒ `k` esce da `deleted`; le foto non hanno flag (il prossimo `HELLO` conferma con il CRC). **S6**: gli esiti aggiornano anche lo snapshot (`onPhotoResult` OK ⇒ `watch.slots[k] = {1, crc}`; `ALBUM_DELETE k` OK ⇒ `{0, 0}` e `k` via da `foreign`), scritto con la sua chiave.
Prima sync dopo una modifica: `webviewclosed` ⇒ `applyPayload` ⇒ `sync.resync()` (= nuovo `JS_READY` → `HELLO` → piano; se una sync è in corso viene ripetuto al termine). `ready` ⇒ `sync.start()` (un secondo `ready` nello stesso runtime ⇒ `resync()`); in modalità dev prima `GET /state.json` (irraggiungibile ⇒ si parte con l'album locale: il percorso "riavvio senza dev server" è quello del telefono). Retry di `index.js` (30 s, 1, 2, 5, 10 min) per classi (§5, 29/08): *link* senza tetto, *photo* al più 3 consecutivi, *permanent* mai (nessun ciclo radio inutile); una sync riuscita cancella il timer.

**Modalità dev** (`Pebble.platform === 'pypkjs'`, `tools/galleria_devserver.py`, §6): il dev server fa le veci della config page: `/state.json` è un payload `full` con `url` al posto di `data`; `album.plan` usa un `loader(slot, fmt, cb)` che scarica `GET /photo/<k>.raw6|raw1?b64=1` e **salva il base64url in `localStorage`** (da lì in poi l'album è identico a quello del telefono); `state.hooks.scenario` (`seq`/`dup`/`crc`/`interrupt`) inietta i guasti di S5a nel motore (solo dev). `showConfiguration` ⇒ `Pebble.openURL('http://localhost:8765/config.html')` (il tool aggiunge `?return_to=http://localhost:<porta>/close?`); la pagina salva con `POST /save` e torna con `return_to + encodeURIComponent('{"v":1,"dev":true,"seq":N}')` (token: il ritorno passa dalla riga di richiesta di `http.server`, ≤ 64 KB); `webviewclosed` con `dev` ⇒ `GET /save.json` (= stato completo) ⇒ `applyPayload(full)` ⇒ `resync()`. Sul telefono (S6) `webviewclosed` porta il payload intero: `r.charAt(0) === '{' ? JSON.parse(r) : JSON.parse(decodeURIComponent(r))`, risposta vuota o non valida ⇒ ignorata con log.

## 10. Rischi e punti aperti ❓
